# ADR 0014: Kits bundle the stack-specific material the engine consumes

## Status

Accepted (2026-09-14).

## Context

The `modernize-*` and `convert-*` flows are technology-neutral; everything
they know about COBOL, ACE, JSP, Spring, Kafka, or Next.js comes from a pack
manifest, its prompt and reviewer sidecars, the scaffold it seeds a target
from, and a deck of translation pattern cards. Until 0.17.0 those pieces
lived in three unrelated places under `flows/` (`packs/`, `fixtures/scaffolds/`,
`patterns/`), the pack pointed at its scaffold with a path that climbed out
of itself, the "universal" pattern deck was in fact COBOL-only, and the
shell shipped all of it to every user as one blob. Packs were also the only
resource with a lookup rule (`LLM4TS_PACK` as a path against the launch
directory, then the flow's directory); scaffolds and patterns had none.

## Decision

A **kit** is a directory with a fixed layout:

```text
<kit>/
  README.md        first paragraph = the kit's one-line description
  packs/<name>/    pack.md + prompts/ + reviewers/ (+ patterns/, lessons.md)
  scaffolds/<name>/
  patterns/        the kit's translation cards
  flows/           optional kit-specific flows (and their lib/)
  fixtures/        optional rehearsal material
```

Kits are discovered in the same three tiers as flows — the project's
`.llm4ts/kits/`, the global `~/.config/llm4ts/kits/`, and the built-in kits
the shell ships beside its engine flows — with project > global > builtin
precedence by kit name. A kit's `flows/` join `llm4ts list` under the kit's
tier, labelled with the kit's name; `llm4ts kits` lists the kits with their
packs and flows.

`LLM4TS_PACK` (and `llm4ts run --pack`) accepts a bare pack name resolved
across the discovered kits, `kit/pack` to name one kit, or a path holding
`pack.md` for a pack still being written. A bare name that two kits of the
same tier both ship is an error naming the candidates; across tiers the
higher tier wins, as for flows. The default pack is `cobol-springboot`.
Scaffold references in `pack.md` stay pack-relative. The pattern cards a
run injects are the pack's own plus its kit's deck; there is no universal
deck.

The engine flows stay in the shell's built-in tier, and the repository ships
two kits, `mainframe-java` and `j2ee-nextjs`, as the built-ins. The layout
is designed so a kit can later be an npm package discovered from
`node_modules` without changing its contents.

## Consequences

- One directory is the unit of "support a new stack": copy a kit, edit its
  packs, drop it under `.llm4ts/kits/`, and the flows find it.
- `@llm4ts/runner/Kits` (discovery, name resolution) and `@llm4ts/runner/Packs`
  (`openPack` over kits, `loadKitPatternCards`) replace the path-only
  `locatePack` roots and `loadUniversalPatternCards`.
- The shell package grows a `kits/` directory; the sync script transpiles
  kit flows and copies the data directories, skipping fixture build litter.
- Anyone who reached into `node_modules/@llm4ts/shell/flows/packs` or set
  `LLM4TS_PACK=packs/<name>` expecting the shipped packs must switch to the
  bare name.

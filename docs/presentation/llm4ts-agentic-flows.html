Agentic engineering workflows

Agents write the code.
Flows make it reviewable.

llm4ts runs coding agents inside explicit, resumable workflows. Every step leaves a file a person can read, and every important decision waits for a person to approve it. Effect-native, agent-agnostic, with review and modernization artifacts as the output, not a chat log.

machine step human decision every step leaves a file

The gap

A coding agent is fast. A team needs more than fast.

One agent in one terminal is a good pair programmer. A real change, an epic with eight stories or a legacy system with four hundred programs, needs things a chat session does not give you:

  • A plan you can read and edit before any code is written.
  • Review that is part of the process, with the findings kept on disk.
  • Work that survives a crash and resumes where it stopped.
  • Freedom to change the agent without rewriting the process.

llm4ts puts the process in code, so the agents can change and the process stays the same.

Four ideas

The whole library rests on four ideas.

Effect-native

A workflow is a typed program

Flows are written in TypeScript on Effect. Failures are typed values, retries and timeouts are explicit, and every dependency can be replaced by a fake, so a flow is tested without a network or a model.

Agent-agnostic

Seats, not vendors

A flow asks for a reasoner to plan, review and judge, and a coder to implement. Claude Code, Codex, Gemini, pi, OpenCode or a local model on your own GPU can fill either seat.

Explicit review

Review is a step, not a hope

Each task passes gates (typecheck, lint, test, build), then review lenses. Each story faces a judge with a rubric. What they did not clear becomes the next revision task.

Artifacts as state

The file is the state

Plans, briefs, findings, verdicts and spec packs are Markdown and JSON in the repository, and the code lands on git branches. Edit a plan and you have approved it. Rerun and the flow resumes from the files.

The vocabulary

Engines know the process. Kits know the technology.

The built-in flows know nothing about COBOL, JSP, Spring or Next.js. Everything specific to a stack is plain text in a kit, so a team teaches the pipeline a new technology by writing documents, not code.

Flow
One TypeScript file that describes a workflow: who plans, who codes, which gates and reviews apply, where people approve. Built-ins can be copied and changed.
Seat
A role in a flow (reasoner, coder, judge) filled by any agent from a roster of executors.
Kit
A folder for one migration path: its packs, the scaffolds that seed a new target, pattern cards, and any flows only that stack needs.
Pack
A manifest plus prompts and reviewers: which files are programs, what the gates are, how the judge scores, what "equivalent" means.
Pattern card
A short translation recipe (a COBOL idiom and its Java form). Only the cards a program matches reach the coder.
Gate, lens, judge
Three levels of review: commands that must pass, focused reviewers per task, and a scored verdict per story.

Flow · epic-stories

One epic, many agents, one branch.

A reasoner splits the epic into stories with declared dependencies and declared file ownership. You approve the plan. Coders then build independent stories at the same time, each in its own git worktree, and each story merges into the epic branch only after its gates, its reviews and its judge agree.

Example epic: “Current account: balance, movements, statements”

task: code, gates, review lenses, commit story judge judge not cleared, revision task merge into the epic branch, gates rerun

Parallel, but fenced

Each story owns its files. A coder that strays outside them is sent back before anything is committed. A merge that turns the epic red is undone and the story revises against the combination that broke.

Visible while it runs

A live agent tree shows every agent in flight, its story and its task. After the run, a profile says where the time went and a cost report gives tokens per run and per model.

A red run teaches the next one

epic-retro reads a failed run, diagnoses each story, and proposes fixes. Once you approve them, the next run applies them. Rerunning skips what already merged.

Flows · modernize-*

From a legacy estate to a proven replacement, in six phases.

The legacy code is read once, on its own side, and turned into a specification pack that people approve. The new system is built from that pack on the other side of a clean-room wall: the target phases refuse to start if legacy source can be reached from there.

Legacy repository

  1. −1 · pack-check

    Does the pack fit this estate?

    Matches the pack's rules against the code. No model call.

  2. 0 · survey

    Inventory and wave plan

    Programs, dependency graph, triage into waves.

  3. ◆ approve

    You approve the waves

  4. 1 · extract

    Spec pack

    Behaviour as specs and BDD scenarios, every rule traced to its source, checked by a judge.

  5. ◆ approve

    You approve the spec pack

clean-room wall

Target repository

  1. 2 · seed

    Scaffold the target

    From the kit's scaffold and the approved pack. No model call.

  2. 3 · implement

    Build behind the gates

    Task by task, with the matching pattern cards in hand.

  3. 4 · verify

    Prove equivalence

    Replay recorded vectors against the new system, measure rule coverage.

  4. 5 · review

    Lens review and lessons

    Findings become fix tasks for phase 3; what was learned goes back into the pack.

  5. ↺ fix tasks return to implement

The bridge · epic-design

Not every program deserves a port.

Some legacy code is dead; some behaviour the new stack already provides. epic-design works through the spec pack with you and writes an epic brief: what is in scope, dropped, provided by the target, deferred. Once you approve it, epic-stories builds that slice in parallel.

What a run leaves behind

The output is a paper trail you can review.

Everything an agent decided is written where people already work: in the repository, next to the code. Reviewers read Markdown, not transcripts. Auditors find the reason for every change. A new agent picks up from the same files.

Why it matters

What a team gets from an agentic flow.

Control

People approve the plan, the brief and the spec pack. Agents do the volume between those decisions.

Throughput

Independent stories build at the same time in isolated worktrees, and only reviewed, judged work reaches the branch.

No lock-in

Swap Claude for Codex, Gemini or a local model per seat. The process, the gates and the artifacts stay the same.

Resumable

A crash, an outage or a red gate is a pause. Rerun and the flow continues from the files, skipping what already merged.

Knowledge that compounds

Kits, packs, pattern cards and lessons hold a team's migration know-how as text, reused on the next estate.

Measured

Traces, cost per run and model, and a time profile. OpenTelemetry export when you want it in your own dashboards.

Agents for the volume.
People for the decisions.

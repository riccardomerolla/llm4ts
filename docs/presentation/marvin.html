DON'T PANIC

A project presentation · agentic engineering

Marvin

Agentic flows that reach the goal, unattended, inside a process you can read.

Hi, I'm Riccardo. This talk is about Marvin: a way of running AI coding agents inside explicit workflows, so that a run can go on unattended and still arrive where it was meant to go.

The name comes from Marvin, the Paranoid Android in The Hitchhiker's Guide to the Galaxy: a brain the size of a planet, given small chores, and convinced it will all go wrong. That is a fair picture of a coding agent today. Very capable, and quite happy to wander off.

This is not a product pitch. I want to explain the method: the ideas, the shape of a run, and what it changed in practice. Ten minutes, eleven slides. The coloured squares orbiting the planet are the states you'll see on every slide.

Two problems kept coming back when I let agents work on their own.

First, on the left: the agent declares the job done when it isn't. It writes “all tests pass” without running them, or finishes three of five features and reports success. Nothing in the loop asks it to prove anything.

Second, on the right: on a long run the agent loses the thread. The goal and the decisions made an hour ago drift out of its working memory, so later steps contradict earlier ones, or it quietly starts solving a different problem.

Both are the same root issue: we trust the agent's own account of the work, and we keep the state of the work inside the agent. The rest of this talk is about moving both of those out of the agent. These two cards are illustrations, not measurements.

The idea

Agents do the volume.
People make the decisions.

The process lives in code. The agents can change. Every step is visible, every finding is written down, and nothing important happens until a person says yes.

The idea is one sentence: agents do the volume, people make the decisions.

The process, meaning the steps, the checks, who approves what, and what gets written down, lives in code, in the repository, next to the project. It is not a prompt and it is not in anyone's head. The agents are the replaceable part: on the right, the seat that writes code changes from one agent to another, and the workflow text doesn't move.

Because the process is explicit, every step is visible and every finding is written to a file. And the decisions that matter, like approving a plan, stay with a person.

The basic loop

Plan, build, check, review. Only reviewed work is committed.

What review does not accept goes back as a revision. The agent never grades its own homework.

    This is the smallest unit of the method, and everything else is built from it.

    An agent writes a plan. An agent builds against it. Then checks run: your build, your tests, the things a machine can verify. Then a separate review looks at the work. Watch the review go red: it found a missing test. That finding is written to a file and goes back to the coder as a revision. The coder fixes it, checks run again, review clears it, and only then is there a commit.

    This answers the first problem from earlier. “Done” is no longer something the agent says about itself. Done means it passed checks and review, and there is a written trail of what was found along the way. Look at the “left behind” list: the plan, the findings from each round, and one commit per reviewed task.

    People approve

    The plan is a document. Editing it is the decision.

    Before any code is written, an agent drafts a plan a person can read. The flow stops and waits. Approve it and the work starts. Send it back and the agent revises it, keeping your edits.

    Wait for a person

    The run pauses on the plan until you answer. Simulated.

    Left behind

      Marvin: They stopped and asked a human. Well, someone has to take the blame.

      Unattended doesn't mean unsupervised. The flow has a few deliberate stops, and the first one is the plan.

      An agent drafts the plan as a normal document in the repository: the stories, who owns which files, in what order. Then the run stops, the yellow node, and waits for a person. Nothing else happens until you answer.

      In the run you see me send it back first. I edited the plan, and the agent revises it while keeping my edits. Then I approve, and the build starts.

      The point is that the decision is made by editing a document, not by chatting with an agent. The plan is readable, it is versioned like code, and it is the thing everyone agreed to. It's also where a team that adopts this spends most of its attention.

      Agents in parallel

      One epic, many agents, one branch.

      Stories declare the files they own and what they depend on. Independent stories are built at the same time, each in its own copy of the repository. A judge scores every story before it merges.

      Stories, three at a time

      Story 1 lays the ground. Stories 2 to 4 run together. Story 5 waits for them.

      Left behind

        Marvin: Five of us at once. Five times the gloom, one branch.

        Real work is bigger than one task, so the plan splits an epic into stories. Each story declares which files it owns and which stories it depends on. That declaration is what makes parallel work safe.

        Watch the run. Story 1 lays the ground: the model everything else needs. Then stories 2, 3 and 4 don't touch each other's files, so they run at the same time, each agent in its own copy of the repository. Story 3 doesn't pass the judge the first time: a gap is written down, it gets a revision, and it passes on the second round. Story 5 depends on all three, so it waits.

        Every story is scored by a judge before it merges into the single epic branch. At the end there is one branch, reviewed story by story, and a report of what ran and where the time went.

        Files are the state

        Stop at any point. Pick up where it stopped.

        Progress is written to files in the repository, not held in an agent's memory. When an agent drops out or a laptop closes, the next run reads the files, keeps what was done, and continues.

        This is the fix for losing the thread: the thread is a file.

        Interrupt and resume

        Halfway through, the agent drops out.

        in the repo

        Marvin: I'll forget everything. Fortunately, the files won't.

        This slide answers the second problem, losing the thread.

        Progress is never kept only in the agent's context. After every task the flow writes where it is to files in the repository: what is committed, what is unfinished, what was decided. On the right you can see that file filling in.

        In the run, the agent goes offline in the middle of task 3. That happens: rate limits, a crash, a laptop lid. I press rerun. The new run doesn't start over and doesn't need anybody to remember anything. It reads the file, keeps tasks 1 and 2 as done, and continues from task 3.

        That's also why long runs stay on track: each step starts from the written record of the goal and the decisions so far, not from a memory that has been fading for hours.

        Because the process is code, the agent is just whoever fills a role.

        A workflow asks for roles: someone to plan and judge, someone to write code. Any coding agent can fill a role: Claude, Codex, Gemini, or a model running on your own machine. In the run you see the coder seat change four times. The plan format is the same, the checks are the same, the review lenses are the same, and the judge uses the same rubric whoever wrote the code.

        This matters for two reasons. Models change every few months, and you don't want your engineering process to be rewritten each time. And it lets a team mix them: a strong model to plan and judge, a cheaper or local one to do the volume.

        Marvin: Old code. Older than me. Nearly as miserable.

        The same machinery applies to modernization, which is where many teams start.

        On the legacy side, agents survey the old code base and turn it into a specification: what each program does, as rules and scenarios, each traced back to the source line it came from. Then a person approves that specification. That's the yellow stop.

        Only the approved specification crosses the clean-room wall. On the new side, agents build the new system without being able to see the old code, and prove it equivalent by replaying recorded behaviour of the old system against the new one.

        The knowledge for each path lives in a kit, like COBOL to Java, JSP to Next.js, SOAP to REST. Inside it a pack defines checks and scoring, and pattern cards translate one idiom each. And not every program deserves a port: the spec is first distilled with a person into an epic brief, what's in scope, dropped or deferred, and the parallel stories build that slice.

        What did this change in practice? Two honest statements, and no more numbers than I can stand behind.

        In general: work that took weeks of development now takes hours of flow runs. The people's time moves to writing and approving the plan and reading the review findings.

        One concrete case: an IBM ACE integration project, built from scratch. The input was a specification. The epic-stories flow, the parallel one from a few slides ago, completed it in about two hours. Compared with that, human-only development took days.

        The bars are deliberately not to scale; the counter is a stylised clock. The precise ratio depends on the project. What doesn't depend on the project is where the time goes: the agents do the volume, and the people's hours go into the decisions.

        DON'T PANIC

        To close, three lines.

        The process is code: steps, checks, approvals and what gets written down live in the repository, versioned, reviewable, and the same for every run.

        The agents are replaceable: any of them can fill a seat, and next year's model drops into the same flow.

        And the record is yours: plans, findings, progress files, verdicts and commits stay in your repository. That's what lets a run go unattended and still be trusted, and it's what lets a person pick it up at any point.

        For the team adopting this: start with the basic loop on one real task, then the plan approval, then parallel stories. Thank you. Questions, and don't panic.
